# Неточности и противоречия материалов кейса Онлайн чаевые

Дата проверки: 7 ноября 2026 года. Проверены основное Word-задание, выданный Python-прототип, шаблоны и четыре исходных CSV. Этот файл фиксирует обнаруженное и не изменяет условия задания. Часть Markdown уже заполнена с помощью ИИ; дополнения, появившиеся при заполнении, отделены от исходных требований в разделе 3.

## 1. Прямые противоречия

### 1.1. T3-1 требует SUCCESS, но формула даёт TIMEOUT

Источники: исходный 03_тесты.md, раздел T3-1; 04_прототип.py, функция emulate_gateway; qr_links.csv, строка qr_001.

- Тест: qr_001, base_amount=637.00, tip_pct=5; ожидаются SUCCESS, tip=31.85, amount_total=668.85.
- В CSV nonce=c82561.
- Формула: h=int(MD5(UTF8(qr_id + nonce)).hexdigest(),16)%10.
- Для qr_001 получается h=9. По заданному распределению 9 означает TIMEOUT, платёж остаётся PENDING.
- Суммы теста верны. Расхождение касается результата шлюза, а не арифметики.

Нельзя одновременно сохранить эту формулу, эти входные данные и получить ожидаемый SUCCESS. В дальнейшей реализации формула и CSV сохраняются; фактическое расхождение отмечается, а не скрывается. Подменяющий ответ тестовый режим не является исходным требованием и не добавляется.

### 1.2. T3-2 требует DECLINED, но формула даёт SUCCESS

Источники: исходный 03_тесты.md, раздел T3-2; 04_прототип.py; qr_links.csv, строка qr_003; payments.csv, строка p_0003.

- Тест: qr_003, base_amount=911.00, tip_pct=15; ожидаются DECLINED и CARD_DECLINED.
- nonce=4443ae; по той же формуле h=7, то есть SUCCESS.
- Чаевые 136.65, итог 1047.65 арифметически верны.
- В историческом payments.csv p_0003 также имеет SUCCESS. Прямой колонки qr_id в этом файле нет, поэтому совпадение номера не доказывает связь записей; оно лишь показывает, что строка p_0003 не является примером отказа.

С теми же входами невозможно одновременно выполнить формулу и ожидание T3-2. Отказ проверяется на исходном QR, у которого действительно h=8; исходный T3-2 остаётся отмеченным как противоречивый пример.

### 1.3. Отмена из PENDING одновременно разрешена и запрещена

Источники: исходный 06_приложение.md, A.3; 02_правила.md, P-4; 03_тесты.md, T3-5; 07_payment_emulator_template.md, матрица переходов.

- A.3 предлагает CREATED → PENDING → SUCCESS / DECLINED / CANCELED.
- P-4 требует CANCEL_NOT_ALLOWED для отмены из PENDING.
- T3-5 требует HTTP 409 для отмены из PENDING.

Для реализации применяется прямо сформулированное P-4, подтверждённое T3-5: отмена только из CREATED. Схема приводится в соответствие с этим правилом. Это выбор между несовместимыми указаниями, а не подтверждение отсутствия противоречия.

### 1.4. Прототип опционален в Word, но требуется в дополнительных критериях

Источники: Задание_T1_Чаевые.docx, «Задача» и «Опциональный продукт»; исходные 02_правила.md, 03_тесты.md, 05_презентация.md и 06_приложение.md.

В Word консольная программа названа опциональной. Шаблоны требуют реализованную идемпотентность, фактические прогоны, скриншоты CLI и коммита. Поэтому дополнительные критерии шире обязательной части Word. Пользователь разрешил продолжить проект; консольная программа выполняется в объёме выданного шаблона, без разработки полноценного сайта или банковской интеграции.

### 1.5. Секрет должен быть вне кода, но записан в прототипе

Источники: 04_прототип.py, SECRET=b"demo-secret-k3"; исходный 11_ИБ.md, раздел 6.

ИБ требует читать секрет через os.environ и не хранить его в Git. Исходный Python содержит демонстрационный ключ строкой. Для проверки выданных подписей требуется именно этот учебный ключ. В доработанном прототипе ключ передаётся через окружение, исходные подписи не пересчитываются. Демонстрационное значение не выдаётся за производственный секрет.

## 3. Что было добавлено при прежнем заполнении Markdown

Следующее появилось в подготовленных мной текстах, но не было точным исходным условием задания:

- Численные ограничения 30 запросов/минуту на сессию и 120 на IP, лимит длины ключа 128 символов, ротация ключей каждые 90 дней. Эти значения были проектными предложениями; их нельзя считать требованиями преподавателя. При дальнейшей сверке они убираются либо помечаются «в исходном задании не задано».
- Управляемый режим, принудительно выдающий SUCCESS или DECLINED для противоречивых примеров. Он был предложен, но не подтверждён заданием. В реализацию не включается.
- Дополнительные коды технических ошибок и десятичное округление HALF_UP — решения для однозначной работы программы, а не цитаты из задания. Они должны быть отделены от кодов и формул, прямо данных в материалах.
- Фиксированная дата в тестах — способ воспроизведения исторических входных данных, не отключение TTL и не настройка обычной оплаты.
- Предложенное распределение задач между четырьмя участниками — не фактический вклад. Реальные сведения заполняет команда.

Эти уточнения нужны, чтобы не смешивать выданные условия, исправление технических ошибок и решения разработчика.

## 4. Границы дальнейшей работы

Доработан исходный CLI: HMAC, срок QR, расчёт и формула эмулятора. Состояния, повтор и отмена описываются как целевая система; заполняется выданная схема API, подготавливаются требуемые диаграммы и материалы защиты. Исходные CSV и Word сохраняются.

Тестовые результаты приводятся фактические. Одновременное полное выполнение взаимоисключающих требований 1.1–1.3 невозможно. Поэтому этот файл прилагается к решению; отметки «пройден» не проставляются вместо реально несовпавших ожиданий. Сведения, для которых нужны участники или преподаватель, не выдумываются.
